# HackAlem AI · анализ изменений и работа с документами

Приложение сравнивает комплекты «до/после», показывает кандидатов на изменения
структуры, потерю и дублирование функций, возможные конфликты и источники.
После проверки человеком выбранные изменения переходят в согласование конкретной
версии, ознакомление сотрудников и пакет документов новичка.

## Быстрый запуск без ключей

Python 3.11, без GPU. Из корня репозитория:

```bash
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
PYTHON_DOTENV_DISABLED=true DEMO_MODE=true streamlit run app/main.py
```

Приложение по умолчанию вызывает адаптер с `use_llm=False`; API не вызывается.
В `app/main.py` отключена автоматическая загрузка `.env` до импорта конфигурации.
Существующий `src/config.py` оставлен без изменений: для самостоятельных запусков
задавайте `PYTHON_DOTENV_DISABLED=true`. Не помещайте секреты в документы или Git.

## Что реализовано

- Загрузка нескольких PDF/DOCX/XLSX/TXT с каждой стороны, безопасные временные
  имена, сброс устаревших результатов при замене файлов. Общий лимит загрузок 50 МиБ.
- Пять вкладок анализа, фильтры находок, источники и журнал фактических этапов.
  Решение пользователя о находке не изменяет `evidence.verified`.
- Локальный анализ реальных текстов через правила и TF-IDF без внешних библиотек
  машинного обучения. Структура и функции извлекаются без встроенных ответов
  на образцы. Цитаты проверяются в исходном документе и пункте после нормализации;
  используется точное вхождение, нечёткая проверка в этом baseline не реализована.
- Карточки «кого затронуло»: исполнитель, было/стало, источники. Ответственный
  явно выбирает изменения и получателей, указывает себя и подтверждает проверку.
- Версия пакета содержит копии оригиналов, карточки, получателей и ответственного.
  Идентификатор зависит от содержимого и номера редакции. Документы «до» доступны
  как основания сравнения. Временные файлы удаляются, оригиналы остаются в памяти сессии.
- Согласование: фиксированный список руководителей, решения и время каждого,
  возврат с обязательным комментарием, журнал. Возврат завершает маршрут;
  повторное согласование требует новой редакции пакета.
- Ознакомление открывается ответственным только после согласования всеми
  участниками. Сотрудник видит назначенные ему изменения и каждый оригинал.
  Отметка относится к сотруднику, документу и точной версии. Вопросы и ответы
  хранятся отдельно и не засчитываются как ознакомление.
- Пакет новичка: ответственный выбирает опубликованные версии, уже адресованные
  сотруднику с той же ролью; доступны оригиналы, карточки изменений, история
  назначений и прогресс по каждому документу. Новая версия не наследует старые отметки.

## Как показать полный сценарий

1. Нажмите «Синтетический пример: подключения и кабельные работы».
   Это **вымышленные** подразделения и обязанности, не регламент Казахтелекома.
2. Посмотрите «Находки» и источники. Ниже, в «Кого затронули изменения», выберите
   карточку, затем явно назначьте одного или нескольких получателей.
3. Укажите название/редакцию пакета и ответственного. Подтвердите проверку
   флажком и нажмите «Создать версию для согласования».
4. Слева откройте «Согласование», выберите версию и начните маршрут. По очереди
   согласуйте её от имени трёх вымышленных руководителей. Можно отдельно
   проверить возврат с комментарием; после возврата создайте новую редакцию.
5. В «Ознакомлении» откройте доступ назначенным сотрудникам. Переключитесь в
   режим сотрудника, задайте вопрос или отметьте ознакомление. Ответственный
   видит прогресс и может ответить на вопрос.
6. В «Документах новичка» назначьте опубликованную версию тому же сотруднику.
   Режим новичка показывает прогресс и позволяет читать и подтверждать документы.

Кнопка «Демо на тестовом комплекте» отдельно анализирует две реальные
обезличенные редакции положения о внутреннем аудите из `data/sample/`.
Эти документы **не подтверждают обязанности монтёров**.

## Архитектура и границы

`app/main.py` → `src/agent.py` → `src.pipeline.run`, если модуль пайплайна есть.
При его отсутствии адаптер использует `app/local_analysis.py`, который читает
документы через существующие `src/parse.py` и `src/structure.py`.
Ошибки установленного пайплайна не маскируются заглушкой. Подключение пайплайна
Бекарыса не требует переписывания интерфейса; его файлы этим расширением не изменены.

`app/workflow.py` сохраняет проверенную версию; `app/approvals.py` отвечает за
согласование, `app/acknowledgements.py` — за ознакомление и пакет новичка.
Старый `run_stub()` сохранён для изолированных регрессионных тестов интерфейса,
но обычные кнопки анализа его не вызывают. Готовый `artifacts/sample_result.json`
не используется и не создаётся. Экспорт DOCX/XLSX и LLM-анализ не добавлены этим расширением.

Локальные правила — ограниченный baseline: они пропускают неявных исполнителей,
сложную морфологию, косвенные связи и часть переформулировок. Совпадение текстов
не доказывает одинаковый смысл, отсутствие совпадения не доказывает потерю.
Создание/упразднение по отсутствию упоминания показывается только как кандидат.
При предупреждении о неполном PDF выводы об отсутствии отключаются.
Ни один результат не объявляется доказанным нарушением. Ответственный проверяет
каждый вывод; отсутствие находок не означает отсутствия рисков.

Согласование и ознакомление — **сессионный прототип**: нет аутентификации,
разграничения реальных пользователей, постоянной БД, внешних уведомлений и
корпоративных интеграций. Выбор участника имитирует вход. Обычная перезагрузка
страницы/потеря сессии может удалить результаты, версии и решения; они не
синхронизируются между браузерами. «Ознакомлен» и «Согласовать» не являются ЭЦП.
Для эксплуатации нужны отдельные авторизация, постоянное хранение и защищённый аудит.

## Проверка

```bash
PYTHON_DOTENV_DISABLED=true DEMO_MODE=true pytest -q
PYTHON_DOTENV_DISABLED=true DEMO_MODE=true python scripts/eval_control.py
```

Контрольный комплект `data/control/` содержит исходную и изменённую синтетические
редакции: переименование подразделения, исчезновение функции, дублирование
и совмещение выполнения/контроля. Ожидания в `expected.json` читает только
оценочный скрипт; анализатор их не использует. Проверяется также правильная
сторона сравнения, пункт и цитата. Тесты охватывают обработку документов,
переходы интерфейса и полный путь от анализа до пакета новичка, версионность,
возврат, вопросы, оригиналы после очистки временных файлов и запуск без API.

## Парсер документов

`python -m src.parse data/sample --limit 10` выводит число фрагментов и первые
10 фрагментов каждого документа. Формат: `doc`, `clause` (без конечной точки),
`text` (с номером пункта), `section` (заголовок вида «3. Заголовок»).
Ненумерованный текст сохраняется с пустым `clause`; неизвестный раздел — пустая строка.
Номера пунктов распознаются и посреди строки. Автоматическая нумерация Word,
не включённая в текст абзаца, не восстанавливается.

## Данные и внешние сервисы

- `python-docx` — текст DOCX, включая таблицы в порядке документа.
- `pymupdf` — текстовый слой PDF; сканы требуют отдельного OCR.
- `openpyxl` — все листы XLSX, включая текст формул.
- TXT читается как UTF-8/BOM или Windows-1251.
- Парсер работает локально, без GPU, API-ключей и внешних сервисов.
- Реальные редакции для интеграционного теста ожидаются в `data/sample/before/`
  и `data/sample/after/`. При отсутствии файлов соответствующий тест пропускается.
- `data/control/` и вымышленные участники — синтетические демонстрационные данные.
  Анализ и сессионные процессы выполняются локально; новых сервисов и библиотек
  расширение не добавляет. Для работы интерфейса и AppTest используется Streamlit 1.64+.
- GitHub Actions запускает тесты и передаёт код проекта в Railway для сборки
  и размещения приложения. Railway CLI закреплён на версии `4.36.1` в workflow;
  локально устанавливать его для автодеплоя не требуется.

## Автодеплой на Railway из приватного репозитория

Workflow [deploy-railway.yml](.github/workflows/deploy-railway.yml) запускает
`pytest -q`, затем деплоит приложение после каждого push в `main` от любого
разработчика. Push с несколькими коммитами деплоит итоговое состояние ветки.
Рабочие ветки не деплоятся; их изменения попадут на сайт после merge в `main`.
Запустить workflow вручную можно на вкладке Actions → Test and deploy to Railway
→ Run workflow, выбрав `main`.

Подключать Railway GitHub App к чужому репозиторию не требуется: GitHub Actions
скачивает код и загружает его через Railway CLI с токеном проекта.
По [документации GitHub](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets),
repository secrets доступны для создания collaborators личного репозитория
и участникам с write-доступом в репозитории организации. GitHub Actions должен
быть разрешён в репозитории; если настройки недоступны, потребуется его владелец.

Однократная настройка:

1. В своём Railway создайте пустой проект и пустой сервис приложения.
   Источник GitHub для этого сервиса подключать не нужно: файлы передаст workflow.
2. В Railway → Project Settings → Tokens создайте **Project Token** для
   окружения `production`. Он определяет проект и окружение без `railway login`
   и `railway link`. Используйте именно project token, не account/API token.
3. Скопируйте ID сервиса приложения в Railway (Copy Service ID).
4. В общем GitHub-репозитории откройте Settings → Secrets and variables → Actions:
   - вкладка **Secrets** → New repository secret: `RAILWAY_TOKEN` — project token;
   - вкладка **Variables** → New repository variable: `RAILWAY_SERVICE_ID` — ID сервиса.
   Токен хранится только в secrets, не в коде или `.env`.
5. Закоммитьте и запушьте workflow, `Dockerfile`, `requirements.txt`, `app/`,
   `src/` и `tests/` в `main`. Railway автоматически использует корневой
   `Dockerfile`; он запускает Streamlit на `0.0.0.0:$PORT`.
6. После первого успешного деплоя в настройках сервиса Railway откройте
   Networking → Generate Domain, чтобы получить адрес приложения.

Без API-ключей приложение работает локально. Текущий UI всегда передаёт
`use_llm=False`, поэтому добавление ключа само по себе не включает модель.
Если позднее будет подключён LLM-режим пайплайна, ключ задаётся через переменные
сервиса и `src/config.py`; для тестов API-ключи не используются.

Статус тестов и отправки смотрите в GitHub Actions, состояние приложения и логи —
в Railway. При ошибке тестов деплой не запускается. Деплои выполняются по одному;
если за время запуска поступило несколько push, GitHub сохраняет только последний
ожидающий запуск. Если сервис уже подключён напрямую к GitHub, отключите для него
прямой автодеплой, чтобы не запускать две сборки одного push.

Документация: [деплой через Railway CLI](https://docs.railway.com/cli/deploying),
[токены Railway](https://docs.railway.com/integrations/api#project-token).
